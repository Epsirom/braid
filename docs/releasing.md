# Releasing

Core, Pi, and DSH are separate public npm packages built from one commit. All use
the same version. The core has no runtime dependencies. Each integration declares
an exact `@chrok/braid` dependency and includes its own compiled integration code.

## Registry and source association

The public packages are [@chrok/braid](https://www.npmjs.com/package/@chrok/braid),
[@chrok/pi-braid](https://www.npmjs.com/package/@chrok/pi-braid), and
[@chrok/dsh-braid](https://www.npmjs.com/package/@chrok/dsh-braid) on npmjs.
DSH joins the coordinated release starting with 0.3.1.
Keep `publishConfig.registry` set to `https://registry.npmjs.org`. All manifests
link to `Epsirom/braid`; integration `repository.directory` values are
`integrations/pi` and `integrations/dsh`.
The repository About website and README badges provide the reverse links.
GitHub Packages is a separate registry and is not a mirror in this release flow.

Package descriptions, keywords, source links, and README content are uploaded
with the package release. A commit on `main` does not update the published npm
metadata. Keep development-version notices accurate until publication, and link
users of the current npm release to its tagged documentation.

To inspect the public release without npm account credentials:

```sh
npm view @chrok/braid dist-tags description repository homepage gitHead dist.attestations --json
npm view @chrok/pi-braid dist-tags description repository homepage gitHead dist.attestations --json
npm view @chrok/dsh-braid dist-tags description repository homepage gitHead dist.attestations --json
```

For a release, query the exact `@X.Y.Z` versions too. Confirm all `gitHead`
values match the release commit, the source links point to this repository, and
provenance identifies this repository's release workflow. The successful
[Publish runs](https://github.com/Epsirom/braid/actions/workflows/release.yml)
and public npm attestations provide release evidence; inspecting or changing
the trusted-publisher account settings requires npm authentication.

## Release notes

[GitHub Releases](https://github.com/Epsirom/braid/releases) are the canonical
release history; there is no separate changelog file. Each release page has
three parts:

1. **Upgrade notes**, from [`.github/upgrade-notes.md`](../.github/upgrade-notes.md):
   only what users must know or do when upgrading, such as required migrations,
   new host or Node.js requirements, and restarting Pi or DSH. The section is
   omitted when the list is empty.
2. **What's Changed**, generated by GitHub from the merged PRs since the previous
   tag and grouped by label using [`.github/release.yml`](../.github/release.yml):
   Breaking Changes, Features, Fixes, Documentation, Dependencies, and
   Maintenance. Each line is the PR title, its author, and the PR link.
3. **New Contributors** and the **Full Changelog** comparison link, also generated.

This keeps release notes short and moves the work into each PR:

- Write the PR title as the release-note line: an imperative summary of the
  user-visible change, for example `Wake the parent when a graph has no active
  work but paused work remains`. Explain details and migration steps in the
  PR description, and keep durable guidance in the docs: migrations belong in
  [compatibility](compatibility.md), linked from the upgrade notes at the
  release tag.
- [Label Pull Requests](../.github/workflows/label-pull-requests.yml) applies one
  category label when a PR is opened, and keeps any category label already set:
  `breaking-change`, `enhancement`, `bug`, `documentation`, `dependencies`,
  `maintenance`, or `skip-changelog` (release PRs). Check it before merging; a
  breaking change is only detected from a `type!:` or `Breaking:` title, so label
  those by hand. PRs labeled `skip-changelog` and PRs by `github-actions[bot]`
  are left out.
- Retitle or relabel a merged PR before publishing if its line would mislead.
  Generated notes credit the PR author and identify first-time contributors
  automatically.

## Prepare a release

Version tags (`v*`) cannot be moved or deleted, and published GitHub releases are
immutable; a correction needs a new version. See [repository settings](repository-settings.md).

1. On a branch from current `main`, run `npm run release:prepare -- <X.Y.Z | patch | minor | major>`.
   Use a minor version for breaking 0.x changes. The script sets every
   `package.json` version, both integrations' exact `@chrok/braid` dependencies,
   the workspace lockfile, `BRAID_VERSION`, and both `REQUIRED_CORE_VERSION`
   constants. It moves version-pinned links in the README files to the new tag,
   moves previous-release links to the current version, and resets
   `.github/upgrade-notes.md` for the new version. It does not commit or push.
2. Write the upgrade notes. Update migration guides, supported Pi/DSH versions,
   package descriptions/keywords, development notices, and ROADMAP status if
   this release changes them.
3. Run `npm ci`, `npm run verify`, and `RELEASE_TAG=vX.Y.Z node scripts/check-release.mjs`
   from the repository root. The package check verifies clean builds, public ESM
   imports, declarations, licenses, Pi/DSH background jobs, and the DSH browser
   entry in temporary consumers outside the checkout. A temporary local registry
   serves the unpublished core tarball; installing either integration tarball must
   fetch core transitively through its version dependency.
4. Inspect `npm pack --dry-run` from the root, `integrations/pi`, and `integrations/dsh`.
   `prepack` rebuilds each package. Never publish stale prebuilt output.
5. Open a PR titled `Release X.Y.Z`; it is labeled `skip-changelog`. Preview the
   generated notes without creating anything, and fix PR titles or labels that
   would read poorly. Merge once CI passes:

   ```sh
   gh api repos/Epsirom/braid/releases/generate-notes -f tag_name=vX.Y.Z -f target_commitish=main --jq .body
   ```
6. Run the [Publish Release](https://github.com/Epsirom/braid/actions/workflows/publish-release.yml)
   workflow with `X.Y.Z`. It finds the commit on `main` that set the version,
   runs the release check there, creates the annotated `vX.Y.Z` tag, and starts
   [Publish](https://github.com/Epsirom/braid/actions/workflows/release.yml) on
   that tag. Publish repeats all checks, publishes the npm packages, then creates
   the GitHub release with the upgrade notes and generated notes, marked latest.
7. Verify all registry versions, `latest` tags, provenance, and a clean install
   before reporting the release complete.

## First publication

Enable two-factor authentication in the npm account's web settings before the
first publish. An emailed login code does not replace enrolling a security key
or passkey for publishing. Complete credential enrollment yourself and keep
recovery codes private.

Log in locally with `npm login --registry=https://registry.npmjs.org`; confirm the
account with `npm whoami`. Publish the core with `npm publish --access public`,
then run `npm publish --access public` from each integration directory. Complete npm's
interactive account/2FA checks if requested. Never put credentials in source,
issues, shell history, or CI logs. An npm registration alone does not guarantee
ownership of a previously used package name.

New packages may temporarily return `E404` after a successful publish while npm
runs its [publish-time scan](https://github.blog/changelog/2026-07-28-npm-publish-time-malware-scanning-and-dual-use-metadata/).
Allow time for the exact versions to become available through `npm view`; do not
republish or bump versions just to work around this delay.

After availability is confirmed, install the registry versions in a fresh project and verify
both exported core entry points and the Pi/DSH integrations. Then create the
corresponding GitHub release.

## Subsequent releases with trusted publishing

For **each** package, configure an npm GitHub trusted publisher:

- Owner: `Epsirom`
- Repository: `braid`
- Workflow filename: `release.yml`
- Environment: leave blank (this workflow does not declare one)
- Allow direct `npm publish`

With npm 11.20 or later, the equivalent CLI setup is:

```sh
npm trust github @chrok/braid --file release.yml --repo Epsirom/braid --allow-publish
npm trust github @chrok/pi-braid --file release.yml --repo Epsirom/braid --allow-publish
npm trust github @chrok/dsh-braid --file release.yml --repo Epsirom/braid --allow-publish
npm trust list @chrok/braid
npm trust list @chrok/pi-braid
npm trust list @chrok/dsh-braid
```

The Publish workflow (`.github/workflows/release.yml`) runs on a stable `vX.Y.Z`
tag: dispatched by Publish Release, or triggered by a maintainer pushing the tag.
Creating a GitHub release by hand no longer publishes to npm. The workflow checks
that the tag is on `main`, validates the tag/version relationship, repeats all
checks, and publishes core then Pi and DSH using short-lived OIDC credentials. After each publish (or retry
of an existing version), it waits for matching version/commit metadata and a
successful tarball download. Integrations are not published until core is available. npm
processing is polled every 15 seconds for up to 10 minutes; a timeout fails the
workflow with retry instructions. It does not require `NPM_TOKEN`.
The workflow installs npm 11 and uses Node 24. See
[npm's trusted publishing documentation](https://docs.npmjs.com/trusted-publishers/).

If a later publish fails, rerun the failed Publish run after resolving the error;
it creates the GitHub release only after all packages are available, and skips
it if the release already exists. Rerunning Publish Release for a version whose
tag already points to the release commit only dispatches Publish again.
The script skips an existing version only when npm records the exact current
Git commit as its `gitHead`. A collision from another commit fails explicitly;
never unpublish/reuse a version to repair it. Publish a new patch instead.

Prereleases are deliberately excluded from the automatic `latest` workflow.
Publish them manually with an explicit tag such as `--tag next` after checks.
